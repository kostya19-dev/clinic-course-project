# Стратегия конкурентного доступа

## Цель

Не допустить, чтобы два пациента были записаны к одному врачу на пересекающиеся интервалы времени, и при этом сохранить согласованность данных при конкурентном доступе.

## Выбранная стратегия

Основной механизм согласованности обеспечивается на стороне PostgreSQL:
- запись выполняется через процедуру `scheduling.book_appointment`
- окончательная защита от конфликта обеспечивается exclusion constraint на `scheduling.appointments`
- проверки доступности и отсутствия врача выполняются внутри процедуры до вставки записи
- backend не пытается разрешать конфликты в памяти

## Почему это подходит для курсовой

- инвариант закреплен в базе данных, а не только в приложении
- решение работает при нескольких экземплярах API
- такой подход легко обосновать в пояснительной записке, потому что согласованность обеспечивается транзакциями и ограничениями
- Go-backend остается тонким и делегирует критическую логику PostgreSQL

## Поведение транзакций

Две конкурентные транзакции могут обе пройти предварительные проверки, но только одна из них сможет зафиксировать конфликтующую запись, потому что exclusion constraint запретит пересечение.

Ожидаемый результат:
- одна транзакция завершается успешно
- вторая завершается ошибкой ограничения PostgreSQL

## Поведение backend

Backend должен:
- вызывать процедуру записи одним обращением к БД
- преобразовывать ошибки ограничений PostgreSQL в HTTP 409 Conflict
- инвалидировать Redis-кэш расписания только после успешной записи

## Уровень изоляции

Рекомендуемая базовая стратегия:
- выполнять запись в транзакционном контексте
- опираться на проверки внутри процедуры PostgreSQL
- использовать exclusion constraint как финальный барьер согласованности

Более строгий уровень изоляции, например `SERIALIZABLE`, можно рассматривать как отдельный исследовательский сценарий, но для текущей курсовой основная стратегия — это транзакционная процедура плюс ограничение пересечения.

## Почему Redis не отвечает за согласованность

Redis используется только для кэширования чтения расписания и прайс-листа.
Он не должен быть источником истины для принятия решения о записи.
Источником истины остается PostgreSQL.
